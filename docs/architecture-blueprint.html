Two requirements files, and the split is the point

requirements-dev.txt is -r requirements.txt plus pytest 9.1.1 and nothing else. The Dockerfile installs requirements.txt alone — a production image has no reason to carry a test runner, and it is extra attack surface plus a bigger download for nothing.

Boot: gates before service

  1. Clamp the logs. The websockets logger is pinned to INFO. At DEBUG the library prints the outbound handshake header by header and redacts nothing — and one of those headers carries OPENAI_API_KEY, beside student traffic, in whatever aggregator the deployment ships to.
  2. Refuse repo credentials in production. production_boot_failures() is raised from the lifespan, so uvicorn never binds a port and the log names every problem it found. It fires on an AUTH_SECRET that is blank, still the published value, an obvious placeholder, or shorter than 32 characters — and on a DATABASE_URL still carrying this repo's dev password.
  3. Warn on an open voice ingress. A blank VOICE_WORKER_SECRET on a non-development ENV leaves the heartbeat and transcript endpoints unauthenticated: a forged heartbeat makes voice report itself available with no worker behind it. A warning, not a refusal — most deployments never enable voice.
  4. Sweep the orphans. Any interview_sessions row a killed process left running is finalized, on a worker thread so a slow database degrades to “swept next restart”, never to “no dashboard”.

Why the boot guard is fatal and has no override flag

AUTH_SECRET signs the reep_session cookie. A production host running on the repo default is one forged {"role":"ADMIN"} cookie away from every student's marks, attendance and USN — no login, no Google round-trip, no database row involved. A warning about that is a line in a log nobody reads.

And on every development ENV the check returns nothing at all. test_boot_guard.py pins that just as hard as it pins the refusal: a guard that trips on a laptop gets deleted by whoever is trying to ship that afternoon.

Alembic enum gotchas — hit repeatedly, so they are written down

a. Adding an enum column to an existing table does not auto-CREATE TYPE — create it first.

b. A new table reusing an existing enum must use postgresql.ENUM(..., name='x', create_type=False); autogenerate emits a bare sa.Enum that errors “type already exists”. Hand-fix it.

c. Two columns sharing one enum reuse a single Enum instance.

05 Identity & scope

Sign-in is Google, for every role, and the roster is the access control. What Google issues is the same session the password path issued — byte for byte — so the require_* dependencies cannot tell the two apart, and did not change.

  1. GET /api/auth/sso/status — a blank client id makes the login screen's Google button render disabled, with the reason. Nothing else is affected.
  2. GET /api/auth/sso/google → 302 to Google, setting a single-use state cookie (its key derived from AUTH_SECRET) and a nonce.
  3. Callback — state cookie checked, then a server-to-server code exchange at oauth2.googleapis.com/token.
  4. Verify the ID token properly — RS256 signature against Google's JWKS, aud = our client id, iss = accounts.google.com, unexpired, email_verified true, nonce matches.
  5. Look the verified email up in users. No matching row ⇒ 302 /login?error=sso_not_enrolled. Nothing self-provisions and no role is ever guessed. GOOGLE_ALLOWED_DOMAIN is a label, not a fence — the row is the whole of the access control.
  6. Issue the session — HS256 JWT, 12 h, claims userId, email, name, role, studentId?, mentorId?, in the httpOnly reep_session cookie, Secure on every non-development ENV.
ElementDetail

Revocationusers.token_version rides in the token. AUTH_REVOCATION_CACHE_SECONDS (default 60) bounds how long a logged-out token still works; a DB read failure admits the session and logs — fails open on purpose.

What is composed into the model's instructions

The base persona verbatim, plus a fixed specialization block, a phase directive and a fixed clarification override. No student transcript is ever composed into them. Three layers close the record, one predicate makes them safe

Consent is a row, not a claim

Three separate booleans — live AI, store transcript, store audio — because they are three different disclosures and one boolean makes “they consented” unfalsifiable. interview_sessions.consent_id pins the exact grant, so “was this student consented, to what wording, at the time of interview X” stays answerable after it has been revoked.

Two directions of failure, chosen deliberately

Opening fails closed (4013) and the mid-interview check fails open (only a real revocation closes with 4014). “We could not check whether they agreed” must never start an interview — and a database hiccup must never end one that a real grant authorised.

The four record tables

interview_sessions (terminal status, phase reached, turns_emitted vs turns_persisted, the consent grant), interview_turns (phase, whether the transcriber heard it, whether it advanced the arc — an empty content is legal and means exactly that), interview_evaluations (nullable scores: a missing score and a zero mean opposite things to a mentor), interview_consents.

Audio, and the column you must branch on

Two WAVs per interview, one per speaker, never mixed — the two directions are not time-aligned. PCM16 LE mono 24 kHz already crosses the relay, so stdlib wave writes the 44-byte header and nothing is encoded. Branch on interview_sessions.audio_recorded, never on audio_path IS NOT NULL — a NULL path collapses four different facts into one.

08 Voice stack — retained, mounted, no UI caller

The LiveKit cascade and the text orchestrator behind POST /api/agent/ask are the rollback path, not dead code. Do not run the voice worker expecting a button, and do not delete either until the interviewer has held up in front of real students.
