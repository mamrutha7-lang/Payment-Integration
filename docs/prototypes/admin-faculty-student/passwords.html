Implementation plan

Activation and passwords

Setting the first password, forgetting it, and changing it — built almost entirely from pieces the codebase already has, with one small decision about how the email leaves the building.

The good news first

Almost all of this is already built. Three pieces exist and are well made:

WhatWhereState
Send-exactly-once mailer — a message can never go twice, however many times a job re-runs app/mailer.pyBuilt. Needs one driver plugged in.
Password hashing — scrypt, and a rule that rejects short or published passwords app/security.py, app/set_password.pyBuilt and correct
Session revocation — one number that logs a user out everywhere users.token_versionBuilt. Already used on logout
Brute-force limiter — 10 wrong tries per account per 15 min app/routers/auth.pyBuilt, and keyed on the account, not the IP

What is missing is small: a way to actually send an email, and a table to hold one-time links.

1 · Sending the email

app/mailer.py was written with the hole already cut for this:

Driver = Callable[[str, str | None], None]
# A driver takes (recipient, subject) and raises on failure.
# None = no-op stub that records the intent without a transport (dev/default).

Whichever option you pick, the job is the same: write one driver, about 40 lines. That is worth saying first, because it means this choice is reversible — swapping providers later is a file, not a project.

OptionCost at your scaleHonest assessment
Amazon SES recommended ~$0.10 per 1,000 emails. A college sending 5,000 a year pays about 50 paise You are already on AWS. Same account, same IAM — and like Bedrock, no API key to paste or rotate, just a task-role permission. Handles bounces and complaints properly, which a plain SMTP relay does not. This is the one I would choose.
The college's own mail server Free — already paid for Genuinely free and keeps student addresses inside the institution. But you inherit its deliverability and its outages, and you need IT to give you a host and a service account. Good fallback, or good first step while SES is being approved.
Resend / Postmark / SendGrid $15–20/month All fine products. But they are a new vendor, a new API key to store and rotate, and a second place student email addresses live — for a job SES already does inside your own account. Hard to justify here.
No email at all Free Main Admin sees the link on screen and hands it over. Keep this regardless of what you choose — see below.
Why SES wins now that paid is allowedThe deciding factor is not price — at this volume every option is effectively free. It is that SES needs no credential: it authenticates through the same task role that already reaches Bedrock, so there is nothing to leak and nothing to rotate. Every other paid option adds an API key someone has to store, and student email addresses to a third party's systems.
One SES catch, plan for itNew SES accounts start in a sandbox that can only send to addresses you have verified. Getting out of it means verifying the bgscet.ac.in domain (DKIM and SPF records — an IT task) and requesting production access, which takes a day or two. Start that request early, and build against the on-screen-link fallback in the meantime so nothing is blocked waiting on it.
Keep the on-screen link permanentlyNot as a stopgap. When a student says "the email never arrived" — and one will — the admin needs to be able to read them the link without waiting on a mail queue. It costs nothing and it is the difference between a five-minute fix and a support ticket.

2 · One new table, three jobs

Activation, forgot-password and any future email confirmation are the same thing: a link that works once and then stops. So it is one table, not three.

auth_tokens
  id
  user_id      → users.id
  purpose      'activation' | 'reset'  — plain text, so a third kind is a row, not a migration
  token_hash   — the link itself is NEVER stored
  expires_at
  consumed_at  — null until used; set once, atomically
  created_at, created_by

Three rules that make it safe

  • The link is stored hashed, never in plain text. Same reason passwords are. If someone reads the database, they get hashes — not a working link into every account with a pending reset. SHA-256 is right here — the token is 256 random bits, not a guessable human phrase, so the slow hashing used for passwords buys nothing and only slows every click.
  • Used once, and the check is atomic. Consume with UPDATE … WHERE consumed_at IS NULL and act on the row count — the same trick the interview code already uses for status = 'running'. Two clicks race; exactly one wins.
  • Short lives. Activation 7 days — a new student may not check mail today. Reset 1 hour — the account already exists and may already be under attack.

3 · The three flows

Details that are easy to get wrong

Never say whether an address exists"Forgot password" must answer "If that address is registered, we've sent a link" — the same words, and roughly the same delay, whether or not the account is real. Otherwise the form becomes a free tool for discovering which students are enrolled.
Reuse what's thereThe new password goes through password_problem(), which already enforces 12 characters minimum and refuses the demo passwords published in AGENTS.md. Note the design screen says "at least 8" — the code's 12 wins; the screen should be corrected, not the rule. And logging other devices out is just token_version += 1, which already exists and is already used by logout.
Rate-limit the request, not just the loginThe existing limiter guards wrong passwords. "Forgot password" needs its own cap — per address and overall — or it becomes a way to send a student a hundred emails.

4 · One decision only you can make

Read this before buildingProduction sign-in is Google-only today. POST /api/auth/login is deliberately refused when ENV=prod, and the roster — not a password — is what controls access. A password system needs that door opened, so this is a decision, not a detail.
OptionWhat it meansTrade
A. Google stays the only way in No student passwords at all. Activation just enrols them; they sign in with the college Google account. Simplest and safest — no password to leak, forget or reset. But it needs every student to have a working college Google account.
B. Google for students, passwords for staff recommended Students use Google. Faculty and admins get password accounts through activation. Smallest password surface, and it covers the people who need access before a Google account exists.
C. Both, for everyone Password sign-in opened in production for all roles. What the design screens assume. Also the widest attack surface, and it weakens "the roster is the access control".

The design's activation screen assumes C. That is a fine answer — but it should be chosen on purpose, because it changes a security property the codebase argues for at length.

5 · Build order

1
The SMTP driver

~40 lines using the standard library, plugged into the seam mailer.py already provides. Nothing else can be tested until mail leaves the building.

2
The auth_tokens table

One migration. Hashed tokens, expiry, single-use.

3
Activation

Admin approve → issue token → email link → student sets password. Plus the on-screen link so the feature works before IT has given you SMTP.

4
Forgot password

Same machinery, one-hour expiry, identical answer either way, its own rate limit.

5
Change password

The simplest of the three — no email, no token. Current password, new password, log the other devices out.

Rough sizeSteps 1, 2 and 5 are small and independent — they can land first and be useful on their own. Steps 3 and 4 are where the care goes, mostly in the details above rather than in volume of code. I am deliberately not putting a number of weeks on this; that depends on who is building and how fast they ship, which I have no read on.
Every claim here was checked against the code: app/mailer.py, app/security.py, app/set_password.py, app/models/user.py, app/routers/auth.py, and the design's StudentActivation screen.
